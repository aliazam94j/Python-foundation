MQTT · Python · paho-mqtt

What every paho-mqtt script is made of

A map of the moving parts: which lines you can never leave out, which are there for comfort, where your Ubuntu / WSL box sits, and how much Python you actually need to start.

01The mental model: three roles

MQTT has exactly three jobs on the wire. Nothing talks to anything directly — every message goes through the middle.

Where Ubuntu / WSL fits

Ubuntu is not the broker. Ubuntu is just the operating system — a place to run programs. The broker is Mosquitto, a specific piece of software you apt install and start. It happens to run inside your WSL Ubuntu, but it could equally run on Windows directly, in Docker, on a Raspberry Pi, or on a cloud server. WSL is just a convenient Linux box to host it on.

So in your setup:

· WSL Ubuntu → the host machine (the "computer" the broker lives on)

· Mosquitto → the broker process, listening on port 1883

· your Python scripts → clients, connecting in as publisher and subscriber

WSL2 forwards listening ports to Windows, so from Windows Python the broker is just localhost:1883.

02The skeleton — five things every script does

Publisher or subscriber, the shape is the same. Change only the last step.

import paho.mqtt.client as mqtt        # 1. import

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)  # 2. make a client

client.connect("localhost", 1883, 60)   # 3. connect: host, port, keepalive

# 4. run the network loop  -- pick ONE style:
client.loop_forever()                        #    blocks here forever (subscribers)
# or
client.loop_start()                          #    background thread (publishers)

# 5. do the actual work:
client.publish("test/temperature", "21.4")   # publisher
client.subscribe("test/temperature")          # subscriber (+ an on_message callback)
  1. 1Import the libraryAlways import paho.mqtt.client as mqtt.
  2. 2Create a client objectIn paho-mqtt 2.x you must pass mqtt.CallbackAPIVersion.VERSION2. This object holds the connection and the callbacks.
  3. 3Connect to a brokerHost and port are the only required arguments. No broker reachable → nothing else works.
  4. 4Run a network loopPaho only sends, receives, and reconnects while a loop runs. loop_forever() blocks; loop_start() runs it on a thread; loop() pumps it manually. Forgetting this is the #1 "why is nothing happening" bug.
  5. 5Publish or subscribeThe one line that decides what this client is. Subscribers also need an on_message callback to actually see the data.

03Required vs. optional, line by line

Required
The import

import paho.mqtt.client as mqtt

Required
A client object

mqtt.Client(mqtt.CallbackAPIVersion.VERSION2) — the version arg is mandatory in 2.x, optional-with-warning is gone.

Required
connect(host, port)

Port defaults to 1883 if you omit it, but you always need a reachable host.

Required
A loop call

loop_forever(), loop_start(), or a manual loop(). Without one, no traffic moves.

Required
publish(...) or subscribe(...)

Plus on_message if you subscribe — otherwise messages arrive and vanish unseen.

Optional
Callbacks — on_connect, on_disconnect, on_publish, on_subscribe

Nice for logging and for subscribing inside on_connect (so it re-subscribes after a reconnect). on_message is the one exception — effectively required for subscribers.

Optional
QoS

Defaults to 0. Pass qos=1 or 2 on publish/subscribe when you care about delivery guarantees.

Optional
keepalive

Third arg to connect(). Defaults to 60 seconds. Rarely need to change it.

Optional
client_id

Auto-generated random id if you don't pass one. Set it (and clean_session=False) when you want the broker to queue messages for you while offline.

Optional
retain=True

On publish, tells the broker to keep the last message on that topic and hand it to any future subscriber immediately.

Optional
username_pw_set(...) / tls_set(...)

Auth and encryption. Not needed for a local Mosquitto with allow_anonymous true; needed for most real / public brokers.

Optional
will_set(...)

"Last will" — a message the broker publishes on your behalf if your client drops without a clean disconnect.

Optional
wait_for_publish() / disconnect() / loop_stop()

Tidy shutdown. Skippable in a quick experiment, worth having in anything long-lived.

04Two things worth knowing early

Topics are slash-separated paths

A publisher always publishes to one exact topic like home/kitchen/temp. A subscriber can use wildcards: + matches one level (home/+/temp), # matches the rest (home/#). Wildcards are subscribe-only.

QoS — how hard the broker tries to deliver

LevelMeaningUse when
0At most once — fire and forget, may be lostFrequent readings where one miss doesn't matter
1At least once — guaranteed, may arrive twiceCommands / events you can't lose (the common default)
2Exactly once — guaranteed, no duplicates, slowestBilling-grade, must-not-double actions

05Easiest vs. how a pro writes it

The short scripts are perfect for seeing the flow. Real deployments add a handful of things on top — none of them change the five-step skeleton, they just help it survive a flaky network and a broker that restarts.

Publisher

Easiest — send one value

import paho.mqtt.client as mqtt

c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
c.connect("localhost", 1883)
c.loop_start()
c.publish("test/temp", "23.4").wait_for_publish()
c.loop_stop()

Production — survives the real world

import logging
import paho.mqtt.client as mqtt

BROKER, PORT = "localhost", 1883
TOPIC = "sensors/livingroom/temp"

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("pub")


def on_connect(c, userdata, flags, rc, props):
    if rc != 0:
        log.error("connect failed: %s", rc)
    else:
        log.info("connected")


client = mqtt.Client(
    mqtt.CallbackAPIVersion.VERSION2, client_id="pub-livingroom"
)
client.on_connect = on_connect
client.will_set(TOPIC + "/status", "offline",
                qos=1, retain=True)   # broker says this if I vanish

client.connect(BROKER, PORT, keepalive=30)
client.loop_start()
try:
    client.publish(TOPIC + "/status", "online", qos=1, retain=True)
    info = client.publish(TOPIC, "23.4", qos=1, retain=True)
    info.wait_for_publish(timeout=5)
finally:
    client.loop_stop()
    client.disconnect()

Subscriber

Easiest — print what arrives

import paho.mqtt.client as mqtt

c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
c.on_message = lambda cl, ud, m: print(m.payload.decode())
c.connect("localhost", 1883)
c.subscribe("test/temp")
c.loop_forever()

Production — keeps working after a drop

import logging
import paho.mqtt.client as mqtt

BROKER, PORT = "localhost", 1883
TOPIC = "sensors/+/temp"

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("sub")


def on_connect(c, userdata, flags, rc, props):
    if rc != 0:
        log.error("connect failed: %s", rc)
        return
    c.subscribe(TOPIC, qos=1)      # re-runs on every reconnect
    log.info("subscribed to %s", TOPIC)


def on_message(c, userdata, msg):
    try:
        value = float(msg.payload.decode())
    except ValueError:
        log.warning("bad data on %s: %r", msg.topic, msg.payload)
        return
    log.info("%s = %.1f", msg.topic, value)


client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2,
                     client_id="temp-logger")
client.on_connect = on_connect
client.on_message = on_message

client.connect(BROKER, PORT, keepalive=30)
client.loop_forever()             # blocks + auto-reconnects

What the pro version adds, and why

Picture the broker as a post office: a topic is an address, publishing is mailing a note, subscribing is filing a mail-forwarding request.

Named constants — BROKER, TOPIC

Code One place to change the address, and the exact same spelling in every file — a typo can't quietly send messages nowhere.

Real life A rubber stamp for the address instead of writing it from memory on every envelope.

on_connect that checks rc (the reason code)

Code You find out whether the connection actually succeeded, instead of charging ahead assuming it did.

Real life Waiting for the call to actually connect before you start talking.

Calling subscribe() inside on_connect

Code Paho re-runs on_connect after every automatic reconnect, so your subscriptions are always restored. Subscribe once at the bottom instead and a single Wi-Fi blip leaves you silently deaf.

Real life The post office cancels your mail-forwarding order when you move out. Re-filing it the moment you move back in means you never miss a letter.

qos=1 on publish and subscribe

Code The broker keeps re-sending until the far side acknowledges. You might get a duplicate; you won't get silence.

Real life Registered mail with a signature on delivery, versus shouting it across a noisy room once and hoping.

will_set(...) — the "last will"

Code You hand the broker a message up front; if your client dies without a clean disconnect, the broker publishes it for you.

Real life A note left with reception: "if I haven't checked in by closing, tell anyone who asks that I've left the building."

retain=True

Code The broker stores the last message on that topic and gives it to any client that subscribes later, straight away.

Real life A whiteboard showing the current reading, versus a one-time PA announcement you only catch if you were in the room.

keepalive=30

Code The client pings every 30 s; hear nothing for ~1.5× that and the broker declares it dead and fires its last will.

Real life A short "still here" check-in call — miss enough of them and they assume you're gone.

client_id="temp-logger"

Code A stable name instead of a random one — needed if you later want the broker to queue messages for you while you're offline.

Real life A named mailbox you rent, instead of grabbing a fresh anonymous PO box every visit.

Guarding the parse in on_message

Code Payloads arrive as raw bytes from anywhere; float(...) inside a try means one malformed message logs a warning instead of killing the listener.

Real life Checking a parcel isn't crushed before you rely on what's inside.

try / finally with loop_stop() + disconnect()

Code The background thread and the socket get released even if something throws partway through.

Real life Hanging up the phone and locking the office on the way out, instead of just wandering off.

logging instead of print

Code Timestamps, severity levels, and one switch to silence it or send it to a file.

Real life A dated logbook versus a drawer of loose sticky notes.

loop_forever() for the subscriber

Code It doesn't only block — it reconnects on its own after a drop, backing off between tries, and then on_connect re-subscribes.

Real life Redialing after 1 s, then 2, then 4 — not hammering redial nonstop, and not giving up after the first failed try.

06How much Python do you actually need?

Not much. paho-mqtt touches a small corner of the language. Here is the honest split — what to be comfortable with before you start, and what you can cheerfully ignore for now.

What you need — and what you don't

Get comfortable with

  • object.method()Make a thing, keep it in a variable, call methods on it: c = mqtt.Client(...), then c.connect(...), c.publish(...). This is 80% of the code.
  • def, and passing a function by namec.on_message = on_message — no parentheses. You hand paho the function and it calls it later. on_message() would call it right now, the classic beginner slip.
  • Strings and f-stringsf"sensors/{room}/temp" to build topic names and message text.
  • bytes vs strPayloads arrive as bytes: msg.payload.decode() for text, then float(...) or int(...) for a number.
  • importJust import paho.mqtt.client as mqtt.
  • while True + time.sleep()Only if you want to publish on a timer.
  • try / exceptThe shape only — to guard a conversion that might fail on bad input.

Skip for now

  • Writing your own class — you use objects, you don't build them
  • Decorators, generators, list / dict comprehensions
  • async / await / asyncio
  • Type hints — def f(x: int) -> str
  • Threads — loop_start() makes one for you; you never touch it
  • Packaging, venv, pip internals (useful later, not now)

The one idea that matters: event-driven code

Most beginner Python runs top to bottom, then stops. paho doesn't. You set up callbacks, hand control to loop_forever() (or loop_start()), and from then on paho calls your functions whenever something happens — a message arrives, the connection drops, a publish is acknowledged.

Rule of thumb: if you can read the two scripts in section 05, and change the topic, the payload, and what happens inside on_message without feeling lost, you already know enough to work here. Fill the other gaps as you hit them.

07Functions: parameters, when and when not

Same rule as C: a parameter exists only if the function's body needs data it doesn't already have. No dependency on outside data → empty parentheses.

Needs a parameter

  • def square(n):Can't compute n * n without knowing n — it has to come from the caller.
  • def is_even(n):The check depends entirely on the value passed in.

No parameter needed

  • def greet():Always prints the same fixed message — nothing from the caller changes what it does.
  • def print_menu():Displays a fixed, hardcoded list. No outside input required.

Takes a parameter

def square(n):
    return n * n

print(square(4))   # 16

Takes none

def greet():
    print("hello")

greet()             # hello

08Functions: return, when and when not

Use return when the caller needs to use the result afterward (store it, print it, pass it on). Skip it when the function's whole job is the side effect itself — printing, saving, sending — and nothing comes back.

Needs return

  • square(n)The caller wants the number back to store, print, or use in more math.
  • is_even(n)The caller needs the True/False to branch on with if.

No return needed

  • greet()Job done the moment it prints. Nothing for the caller to use afterward.
  • client.loop_start()Starts a background thread as a side effect — there's no value to hand back.

C parallel: a Python function with no return behaves like C's void f(...). Under the hood it still returns something — the special value None — but you're not meant to use it.

09For loops: don't name the loop variable after the list

for X in Y: means two different things happen to X and Y. Mixing up their names hides that difference.

What actually happens: Python looks at Y once, right when the loop starts, and builds an internal iterator over whatever list Y pointed to at that moment. Then, on every pass through the loop, it takes the next value from that iterator and stores it in X — overwriting whatever X used to hold.

If X and Y are the same name, the iterator still works fine (it already grabbed the list before anything got overwritten) — but by the end of the loop, that name no longer points to your list. It points to the last value the loop produced instead.

Confusing — happens to work

nums = [20, 21, 22, 25, 10, 6]

for nums in nums:
    if nums % 2 == 0:
        print(nums)

# loop output is fine: 20, 22, 10, 6
# but afterward: nums == 6
# the original list is gone —
# "nums" now means one number, not six

Clear — list stays intact

nums = [20, 21, 22, 25, 10, 6]

for num in nums:
    if num % 2 == 0:
        print(num)

# loop output: 20, 22, 10, 6
# afterward: nums is still
# [20, 21, 22, 25, 10, 6]

Rule of thumb: the thing after in is the collection (plural — nums, items, users). The thing before in is one element of it (singular — num, item, user). Different names, on purpose, every time.

10Parameters vs. C, six cases side by side

Same question every time: does the function's body need a value it doesn't already have? Green means yes, amber means no — and the C version makes the same call, it just also has to spell out the types.

1. Square a number

Needs parameter

Python

def square(n):
    return n * n

C

int square(int n) {
    return n * n;
}

2. Greet with a fixed message

No parameter

Python

def greet():
    print("hello")

C

void greet(void) {
    printf("hello");
}

3. Check if a number is even

Needs parameter

Python

def is_even(n):
    return n % 2 == 0

C

int is_even(int n) {
    return n % 2 == 0;
}

4. Ask the user for a number

No parameter

Python

def get_number():
    n = int(input("n? "))
    return n

C

int get_number(void) {
    int n;
    scanf("%d", &n);
    return n;
}

Gets its own data from the user instead of the caller — so nothing needs to be passed in, even though it still returns a value.

5. Print a fixed menu

No parameter

Python

def print_menu():
    print("1. Start")
    print("2. Quit")

C

void print_menu(void) {
    printf("1. Start\n");
    printf("2. Quit\n");
}

6. Add two numbers

Needs parameters

Python

def add(a, b):
    return a + b

C

int add(int a, int b) {
    return a + b;
}

Two pieces of missing information → two parameters. Nothing caps it at one.
